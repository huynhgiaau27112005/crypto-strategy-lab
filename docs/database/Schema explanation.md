# Crypto Strategy Lab — Database Documentation

## 1. Overview

Database stack:

- **PostgreSQL**
- **TimescaleDB** for time-series market data
- **DBML** as the logical schema source

The current database is designed around the following flow:

```text
Authenticated User
       │
       ▼
Search Configuration
       │
       ├── Timeframe
       ├── Timestamp range
       ├── Selected strategies
       ├── Weight ratio
       └── Iteration limit
       │
       ▼
  Search Engine
       │
       ├── Iteration 1 → Candidate 1 → Backtest → Evaluation
       ├── Iteration 2 → Candidate 2 → Backtest → Evaluation
       ├── Iteration 3 → Candidate 3 → Backtest → Evaluation
       └── ...
       │
       ▼
   Leaderboard
```

The important distinction is:

> **Strategy = reusable strategy type. Candidate = concrete parameters generated by the Search Engine.**

For the current project, the basic strategies are:

```text
MA
RSI
BB
```

The Search Engine generates concrete variants such as:

```text
MA20
MA50
RSI14
RSI21
BB20
BB30
```

These variants are **not separate rows in `strategies`**.

# 3. Users and Authentication

## `users`

Every person using the system must have an account.

```text
users
├── id
├── email
├── password_hash
├── display_name
├── status
├── created_at
└── updated_at
```

The most important fields are:

| Field | Meaning |
|---|---|
| `id` | Unique user ID |
| `email` | Login identifier |
| `password_hash` | Securely hashed password |
| `status` | Account state |
| `created_at` | Account creation time |

Passwords must never be stored as plaintext.

### Ownership

User-owned entities reference:

```text
users.id
```

For example:

```text
users
 ├── experiments
 └── strategies
```

---

## `refresh_tokens`

This table is used when the authentication system persists refresh tokens.

```text
users
   │
   └──< refresh_tokens
```

Only a hash of the refresh token should be stored.

# 4. Market Data

## `candles`

`candles` stores shared OHLCV market data.

```text
candles
├── timeframe
├── timestamp
├── open
├── high
├── low
├── close
└── volume
```

Example:

```text
timeframe = 5m
timestamp = 2026-08-20 10:00:00
open      = 112000
high      = 112500
low       = 111800
close     = 112300
volume    = ...
```

The data is shared between users.

There is intentionally no:

```text
user_id
```

in `candles`.

---

## TimescaleDB

The `candles` table should be converted into a TimescaleDB hypertable using `timestamp`.

Conceptually:

```text
candles
   │
   ▼
TimescaleDB Hypertable
   │
   ├── historical data
   ├── time-range queries
   └── timeframe queries
```

Example migration:

```sql
SELECT create_hypertable(
    'candles',
    by_range('timestamp')
);
```

The exact TimescaleDB migration should be kept in the database migration files rather than in the DBML.

# 5. Strategies

## `strategies`

This table represents reusable strategy implementations.

For the current project, the main built-in strategies are:

```text
MA
RSI
BB
```

The database should **not** contain:

```text
MA20
MA30
MA50
RSI14
RSI21
BB20
BB30
```

as separate strategies.

Instead:

```text
strategies
       │
       ├── MA
       ├── RSI
       └── BB
```

The Search Engine generates the concrete parameters.

---

## Why separate Strategy and Candidate?

Suppose the Search Engine generates:

```text
Candidate #1

MA:
  period = 20

RSI:
  period = 14

BB:
  period = 20
```

Another iteration generates:

```text
Candidate #2

MA:
  period = 50

RSI:
  period = 21

BB:
  period = 30
```

Both Candidates reuse:

```text
MA
RSI
BB
```

but have different parameters.

Therefore:

```text
Strategy
    = what algorithm is used

Candidate
    = which parameters were selected for one Search iteration
```

# 6. AI Strategy

The system also supports:

```text
AI_GENERATED
```

strategies.

The flow is:

```text
Authenticated User
       │
       │ natural-language description
       ▼
   AI Generator
       │
       │ generated Python
       ▼
AI_GENERATED Strategy
```

The strategy stores:

```text
description
source_code
language = PYTHON
owner_user_id
```

Only an authenticated user can save an AI-generated strategy.

AI-generated Python should not be executed directly inside the main API process. Execution should happen in an isolated worker/sandbox.

# 7. Experiments

## `experiments`

An Experiment represents one Search Run.

```text
users
  │
  └── experiments
```

It contains the lifecycle state of the Search Engine:

```text
CONFIGURED
RUNNING
PAUSED
COMPLETED
FAILED
CANCELLED
```

There is deliberately **no `search_engine` column**.

The project currently has only one Search Engine implementation.

---

# 8. Search Configuration

## `experiment_configs`

Before starting the Search Engine, the user defines the configuration.

Typical configuration:

```text
Timeframe:
    5m

Timestamp:
    2026-01-01 → 2026-07-01

Iterations:
    50

Strategies:
    MA
    RSI
    BB

Weights:
    MA  = 0.30
    RSI = 0.30
    BB  = 0.40
```

The configuration is associated one-to-one with an Experiment:

```text
experiments
     │
     └── experiment_configs
```

The configuration should be treated as immutable once the Search Run starts.

---

# 9. Selected Strategies and Weight Ratio

## `experiment_config_strategies`

This table defines which strategies the user selected and their weight.

Example:

```text
Experiment Config #1

MA
weight = 0.30

RSI
weight = 0.30

BB
weight = 0.40
```

Database representation:

```text
experiment_config_strategies

experiment_config_id | strategy_id | weight
---------------------|-------------|-------
config-1             | MA          | 0.30
config-1             | RSI         | 0.30
config-1             | BB          | 0.40
```

The weight is a property of the **Search Configuration**, not of the Candidate.

This is important.

Every Candidate generated under the same configuration uses the same weight ratio.

Recommended rule:

```text
weight >= 0
SUM(weight) = 1
```

For example:

```text
0.30 + 0.30 + 0.40 = 1.00
```

---

# 10. Iterations

## `experiment_iterations`

The Search Engine works in iterations.

Each iteration generates exactly **one Candidate**.

Example:

```text
Experiment #1

Iteration 1 → Candidate #1
Iteration 2 → Candidate #2
Iteration 3 → Candidate #3
...
Iteration 50 → Candidate #50
```

The table stores:

```text
iteration_number
status
started_at
completed_at
error_message
```

Possible states:

```text
PENDING
RUNNING
COMPLETED
FAILED
```

---

# 11. The `+10 Iterations` Feature

The `+10` button does **not** create a new Experiment.

Suppose:

```text
iteration_limit = 50
```

The Search Engine generates:

```text
1 → 50
```

The user presses:

```text
+10
```

The limit becomes:

```text
60
```

and the Search Engine continues:

```text
51 → 60
```

The same objects remain:

```text
Experiment #1
Config #1
Leaderboard #1
```

Only additional iteration records are created.

```text
Experiment #1
│
├── Iteration 1
├── ...
├── Iteration 50
├── Iteration 51
├── ...
└── Iteration 60
```

No new table is necessary for iteration batches.

---

# 12. Candidates

## `candidates`

A Candidate is the **result of one Search Engine iteration**.

Relationship:

```text
experiment_iteration
        │
        │ 1 : 1
        ▼
    candidate
```

Therefore:

```text
Iteration 1 → Candidate 1
Iteration 2 → Candidate 2
Iteration 3 → Candidate 3
```

A Candidate is not manually created during the normal Search flow.

It is generated automatically.

---

# 13. Candidate Parameters

## `candidate_strategies`

This table stores the concrete parameters generated by the Search Engine.

Example:

```text
Candidate #1

MA:
{
  "period": 20
}

RSI:
{
  "period": 14
}

BB:
{
  "period": 20
}
```

Another Candidate:

```text
Candidate #2

MA:
{
  "period": 50
}

RSI:
{
  "period": 21
}

BB:
{
  "period": 30
}
```

Therefore:

```text
candidate_strategies
├── candidate_id
├── strategy_id
└── parameters
```

The `parameters` field is `jsonb` because different strategies can have different parameter sets.

For example:

```json
{
  "period": 20
}
```

or:

```json
{
  "period": 14,
  "oversold": 30,
  "overbought": 70
}
```

or:

```json
{
  "period": 20,
  "stddev": 2
}
```

---

# 14. Weight vs Parameters

This distinction is critical.

### Configuration

```text
MA weight  = 0.3
RSI weight = 0.3
BB weight  = 0.4
```

Stored in:

```text
experiment_config_strategies
```

### Candidate

```text
MA period  = 20
RSI period = 14
BB period  = 20
```

Stored in:

```text
candidate_strategies
```

So:

```text
Search Configuration
        │
        ├── MA weight = 0.3
        ├── RSI weight = 0.3
        └── BB weight = 0.4

Candidate #1
        │
        ├── MA period = 20
        ├── RSI period = 14
        └── BB period = 20
```

This allows the Search Engine to explore parameter combinations while maintaining the user's configured strategy weighting.

# 15. Automatic Backtesting

After a Candidate is generated:

```text
Search Engine
      │
      ▼
Candidate
      │
      ▼
Backtest Worker
```

The backtest runs in the background.

The API should not need to keep the original Search request open until all iterations finish.

---

# 16. `backtest_runs`

This table represents the background execution state.

```text
candidate
   │
   └── backtest_run
```

Possible states:

```text
PENDING
RUNNING
COMPLETED
FAILED
```

Example:

```text
Candidate #50

backtest:
    status = RUNNING
```

The frontend can use this state to display:

```text
Iteration 50
Candidate generated ✓
Backtest running...
```

# 17. Trades

## `trades`

When the Backtest Worker simulates the Candidate, it produces trades.

```text
Backtest Run
    │
    ├── Trade 1
    ├── Trade 2
    ├── Trade 3
    └── ...
```

A trade contains:

```text
side
entry_time
entry_price
quantity
stop_loss
take_profit
exit_time
exit_price
profit_loss
return_pct
exit_reason
```

---

# 18. Evaluations

## `evaluations`

Once a backtest finishes, the system calculates evaluation metrics.

Example:

```text
Total Return
Profit/Loss
Win Rate
Maximum Drawdown
Number of Trades
Profit Factor
Sharpe Ratio
Overall Score
```

Relationship:

```text
Candidate
   │
   ▼
Backtest
   │
   ▼
Evaluation
```

The `overall_score` is particularly important because it can be used to rank Candidates on the Leaderboard.

# 19. Leaderboard

## `leaderboards`

A Leaderboard belongs to an Experiment.

```text
Experiment
    │
    └── Leaderboard
```

This means the Leaderboard represents:

> The ranking of Candidates generated and evaluated under one Search Configuration.

For example:

```text
Experiment #1
Config:
  MA  = 0.3
  RSI = 0.3
  BB  = 0.4

Leaderboard #1
```

# 20. Changing Configuration

Suppose the user starts with:

```text
MA = 0.3
RSI = 0.3
BB = 0.4
```

and then changes it to:

```text
MA = 0.6
RSI = 0.2
BB = 0.2
```

This is **not** an update to the existing running Experiment.

Instead:

```text
Experiment #1
Config #1
MA .3 / RSI .3 / BB .4
        │
        └── Leaderboard #1


Experiment #2
Config #2
MA .6 / RSI .2 / BB .2
        │
        └── Leaderboard #2
```

The old Leaderboard can be hidden/archived from the UI.

It is preferable to retain the old database records because this preserves historical results and reproducibility.

---

# 21. Changing Timestamp or Timeframe

The same rule applies if the user changes:

```text
timeframe
start_time
end_time
```

For example:

```text
Experiment #1
5m
Jan → Jun
```

then:

```text
Experiment #2
1h
Jan → Jun
```

These are different Search Runs.

The second run should not mutate the first configuration.

# 22. Complete Search Engine Flow

The complete backend flow is:

```text
User
 │
 │ configure
 ▼
Experiment
 │
 └── Experiment Config
       │
       ├── Timeframe
       ├── Start timestamp
       ├── End timestamp
       ├── Iteration limit
       ├── MA
       ├── RSI
       ├── BB
       └── Weight ratios
              │
              ▼
         Search Engine
              │
              ▼
        Generate Iteration
              │
              ▼
           Candidate
              │
              ├── MA parameters
              ├── RSI parameters
              └── BB parameters
              │
              ▼
        Background Backtest
              │
              ▼
            Trades
              │
              ▼
          Evaluation
              │
              ▼
          Leaderboard
```

The loop continues until:

```text
current_iteration >= iteration_limit
```

If the user presses `+10`:

```text
iteration_limit += 10
```

and the Search Engine continues.

# 27. Why This Design

The database intentionally separates four concepts:

### Strategy

```text
What strategy exists?
```

Example:

```text
MA
RSI
BB
```

### Configuration

```text
How should the Search Engine search?
```

Example:

```text
MA = 30%
RSI = 30%
BB = 40%

5m
Jan → Jul
50 iterations
```

### Candidate

```text
What concrete strategy combination did the Search Engine generate?
```

Example:

```text
MA20
RSI14
BB20
```

### Experiment

```text
Which Search Run produced these Candidates?
```

This separation prevents the database from mixing:

```text
strategy definition
```

with:

```text
Search configuration
```

and:

```text
Search result
```

---

# 28. Important Database Constraints

The application/migrations should enforce at least:

```text
1. users.email is unique

2. SYSTEM strategies have no owner

3. USER strategies have an authenticated owner

4. AI_GENERATED strategies have an authenticated owner

5. AI_GENERATED strategies use Python

6. experiment end_time > start_time

7. iteration_number is unique inside an Experiment

8. Each iteration has at most one Candidate

9. Each Candidate has at most one Backtest Run

10. Each Backtest Run has at most one Evaluation

11. Strategy weight >= 0

12. Sum of selected strategy weights = 1

13. iteration_limit > 0

14. Leaderboard belongs to exactly one Experiment

15. A leaderboard entry references a Candidate belonging to
    the same Experiment as the Leaderboard
```

The last constraint is especially important because DBML cannot conveniently express every cross-table business rule.

# 29. Reproducibility

The structure supports reproducibility:

```text
Leaderboard
     │
     ▼
Candidate
     │
     ▼
Iteration
     │
     ▼
Experiment
     │
     ▼
Configuration
     │
     ├── timeframe
     ├── timestamp range
     ├── selected strategies
     └── weights
```

And the Candidate stores the exact parameters generated by the Search Engine:

```text
Candidate
 ├── MA → {"period": 20}
 ├── RSI → {"period": 14}
 └── BB → {"period": 20}
```

Therefore the system can later determine:

```text
Why did this Candidate receive this score?
```

without needing to regenerate it.
